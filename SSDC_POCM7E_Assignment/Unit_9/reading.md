Bogner, Kotstein and Pfaff’s (2023) design rules are highly relevant to my API because the system is intended to support distributed use, where clarity, consistency and predictable behaviour are essential. In a distributed environment, APIs act as the contract between components, so poorly designed endpoints, inconsistent naming, or unclear resource structures can quickly reduce maintainability and increase the risk of misuse. Bogner et al. found that violations of RESTful design rules generally made APIs harder to understand, with 11 of the 12 tested rules producing significantly worse comprehension results. This is directly applicable to my system, because an API for creating and reading records must be easy for other developers, services, or clients to interpret correctly. Applying these rules would therefore improve usability, reduce integration errors, and support more standardised service deployment across distributed components. In practice, this means using clear resource-oriented URIs, appropriate HTTP methods, consistent parameter naming and predictable response structures so that the API remains understandable, extensible and less error-prone as the system grows (Bogner, Kotstein and Pfaff, 2023). The module also places explicit emphasis on using Flask to create an API and on designing an ontology for standardised service deployments, so the relevance of understandable and consistent API design is central to the intended learning outcomes.

The evolution from monolithic architectures to distributed systems and microservices reflects a fundamental shift in how scalability, resilience and maintainability are achieved in modern software engineering. Monolithic systems, while simpler to design and secure in a centralised manner, suffer from limited scalability and tight coupling, which restrict flexibility and increase deployment risk. In contrast, distributed architectures and microservices enable independent scaling, fault isolation and faster development cycles, but introduce significantly greater complexity and an expanded attack surface. Each service communicates over a network, making data in transit a primary security concern and necessitating robust encryption mechanisms such as TLS and secure key exchange strategies. Furthermore, distributed environments are particularly vulnerable to attacks such as man-in-the-middle interception, API abuse, service impersonation and lateral movement across compromised services. Virtualised environments and container-based deployments introduce additional risks, including hypervisor attacks, container escape and misconfigured orchestration platforms. As a result, security must be embedded at multiple layers, including network segmentation, identity and access management, secure service-to-service communication and continuous monitoring. This shift demonstrates that while distributed architectures offer clear operational advantages, they demand a more sophisticated and layered security approach to effectively manage the increased risk landscape.
