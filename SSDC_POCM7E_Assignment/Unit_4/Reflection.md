# Unit 4 – Reflection

Unit 4 changed my understanding of software security in a more practical way than the earlier units. In Units 1 to 3, much of the emphasis was placed on secure software development at a higher level, including organisational culture, SDLC choices, modelling, and programming language concepts. Those themes were important, but Unit 4 made security feel far more concrete. It shifted my attention from abstract principles towards implementation details that can create measurable technical risk.

The most important insight I gained in this unit concerns regular expression attacks, particularly Regular Expression Denial of Service (ReDoS). Before studying this topic, I had a general understanding that regular expressions could be inefficient or badly written, but I had not fully appreciated that they could become a direct security problem. In practice, I had mainly viewed regex as a validation tool used to improve input handling. I now understand that poorly designed regular expressions can themselves become an attack surface.

This was a significant gap in my prior knowledge. I already understood more familiar secure coding concerns such as input validation, SQL injection, dependency risk, and insecure coding patterns. However, I had not previously examined in enough depth how catastrophic backtracking can be triggered deliberately by crafted input, leading to excessive CPU consumption and denial of service. What stood out to me is that this is not simply a performance defect. It is a security weakness because it affects availability, which is one of the core dimensions of information security.

This unit also helped me understand that security problems are not always obvious from reading code casually. A regular expression may appear compact and harmless while still containing structural properties that make it dangerous under specific conditions. That reinforced an important lesson for me: code that looks efficient or elegant is not necessarily secure. In the context of regex, the underlying execution behaviour matters as much as the syntax itself.

Another valuable insight was the relationship between code quality and security. I found the discussion around code smells, static analysis, testing, and cyclomatic complexity particularly useful because it showed that maintainability and security are closely linked. I had already seen poor structure as a maintainability concern, but Unit 4 strengthened my understanding that maintainability also functions as an indirect security control. When code becomes too complex, difficult to read, or difficult to test, the probability increases that security-relevant defects will remain unnoticed.

The unit also sharpened my view of testing. I was reminded that test coverage alone can give false confidence. A codebase may appear well tested while still missing dangerous edge cases, malformed input, or hostile inputs specifically designed to trigger failure conditions. In relation to regex, that means validation logic should not only be tested against expected input, but also against adversarial and boundary cases. This is a mindset I will take forward, because it aligns better with real-world threat conditions.

What I found especially useful was the idea that static analysis and dynamic analysis should not be treated as competing approaches. Instead, they complement one another. Static analysis can identify suspicious patterns early, but it may miss runtime behaviour or produce false positives. Dynamic analysis can reveal actual behaviour under hostile input, but only after execution. The combination is therefore much stronger than either approach used alone. This gave me a more mature understanding of secure verification: no single tool or technique is sufficient in isolation.

From a professional perspective, this unit has changed how I will think about validation logic in future software work. I will no longer treat regular expressions as low-risk helper constructs. Instead, I will treat them as components that require review, bounded design, and testing under misuse conditions. Where possible, I would now favour simpler and more predictable validation approaches over complex expressions that are harder to reason about. If regex is used, I would want to assess whether the pattern can backtrack excessively, whether input length should be constrained, and whether time or resource limits are needed at system level.

Overall, Unit 4 deepened my understanding of security by showing that vulnerabilities can emerge from design choices that many developers might dismiss as minor implementation details. The most important learning outcome for me was recognising that regex can be weaponised, and that availability failures deserve the same seriousness as confidentiality and integrity failures. This unit therefore strengthened both my technical awareness and my judgement. It reminded me that secure software development depends not only on broad principles, but also on careful attention to the hidden behaviour of small coding decisions.
